## How to read this

Each phase has a **goal**, a **scope** (what's actually in it), and an **exit gate** (the concrete condition that must be true before moving to the next phase). A phase isn't "done" because time was spent on it — it's done when its exit gate passes, verified live, not assumed from reading code.

Every phase, before being marked complete, must pass the **standing verification bar**:
- `npx tsc --noEmit` — zero errors
- `npx eslint .` — zero errors (warnings tolerated in old scratch scripts only, never in `src/`)
- `npm run backtest` — 0 failing checks
- Whatever the phase actually built has been exercised live (a real API call, a real dispatch, a real browser check) — not just read and assumed correct.

## Phase 1 — Core Capability Growth (NEXT)

**Goal:** The system does more real work, not just more honest reporting of the work it already does.

**Scope:**
1. **n8n automation department, real execution.** Today, AI Systems/Automation can *propose* n8n workflow templates (`n8n_template_ingestor`) inside a department draft. This phase turns that into real execution: an approved workflow can actually be created/activated in n8n, gated behind the existing approval mechanism (`approvalStore.ts` / `ApprovalBanner`) — never auto-executed without a human saying yes.
2. **Decide on OpenRouter credits.** Free-tier limits are hit on nearly every real job right now. This is a cost/quality decision for you, not a code change — but it directly affects how good Phase 1's output looks, so make the call before or during this phase, not after.
3. **Re-run the backtest suite after n8n execution lands**, using a fixture brief that specifically exercises automation, to catch anything Phase 0's fixtures wouldn't.

**Exit gate:** A real n8n workflow gets created and activated end-to-end from a real job, through the real approval gate, verified by actually checking the n8n instance afterward — not just checking that the code path returns 200.

**Status (2026-09-16/17):**
- Item 2 (OpenRouter credits) — decided: staying on the free OpenRouter/Ollama tier for now, accepting the reliability tradeoff that comes with it. Revisit only if/when a paid key gets added for speed, not urgency.
- Item 1 (n8n real execution) — the tool code itself is now proven genuinely correct end-to-end (create → activate → execute, each independently verified against n8n's own API, including fixing a real bug where `execute` called an endpoint n8n's public API doesn't have). What's **not** yet proven is a real department reliably calling that tool unprompted during an actual job — free-tier models have so far either picked the wrong department or written prose instead of calling the tool, across several attempts, even after two rounds of prompt fixes (task framing, token budget, department-selection cap). The literal "from a real job" exit-gate wording is therefore not strictly met yet — it's tool-level proven, not reliably model-driven proven.
- Item 3 (automation-focused backtest fixture) — not done. Low priority now given the above; would mostly re-demonstrate the same model-reliability gap rather than the tool's correctness, which is already independently proven.

**Decision:** treating Phase 1 as closed enough to move forward — the remaining gap is explicitly accepted, not unresolved. Revisit item 1's strict exit gate if/when a stronger model is in the loop.

## Phase 4 — Real Capability Expansion

**Goal:** Give agents more real things to actually do, gated behind the user's own credentials — before Phase 5 builds a beautiful way to watch them do it. Visualizing work that isn't real would repeat exactly what Phase 0 tore out.

**Scope:**
1. **Meta Ads integration** — Meta's official Ads MCP server (`mcp.facebook.com/ads`, launched April 2026, OAuth-based, 29 tools spanning campaign management, reporting/insights, catalog ops, account diagnostics). Same "OAuth — coming soon" bucket as Google Drive/Gmail/Slack already in the connector catalog. Strictly optional per user — without it, the relevant department stays a research-backed consultant/advisor rather than an operator of the account.
2. **Per-agent bring-your-own-key capability routing** — e.g. image generation: if the user supplies a ChatGPT/Gemini/Higgsfield (or similar) key, the responsible agent uses it for real generation; if not, a built-in free model handles it. Generalizes the pattern already used for LLM provider keys to per-capability tool keys.
3. **Master cross-agent findings/audit document** — every agent's real-time findings roll up into one summarized, audited view across the whole job, not just per-department output.
4. **On-demand vault activation via retrieval-based routing** (specified 2026-09-17, refines Phase 2's "vault stays reference-only" decision rather than reversing it). The user's ask: all 279 vault specialists should be *available and callable at all times*, without every job having to consider (or pay for) all 279 at once. Concrete design, worked out with the user:
   - **Per-agent capability record.** Every vault file gets a structured entry (not just prose) covering: role/skills summary, required tools/APIs, and an approval tier (read-only / needs-approval-to-act) — the same schema this phase's item 2 (BYO capability keys) already needs, so this isn't new infrastructure, it's reusing it.
   - **A narrowing step before the LLM ever chooses.** When HQ plans a job, a cheap, deterministic keyword/semantic match over the 279 capability records narrows the field to the genuinely relevant candidates (roughly 10-20) *before* any LLM has to decide anything — the 279 are never dumped into one prompt at once. HQ then makes its real dispatch decision from that short, pre-filtered list, the same way it already picks from the 8 departments today.
   - **Why this is necessary, not optional polish:** the risk isn't that the vault's roles are unclear (they're already reasonably well-labeled) — it's that asking an LLM to reliably pick the right few out of 279 raw options in a single pass degrades regardless of label quality (well-documented long-list selection failure), and this project runs on free-tier models by deliberate choice (see Phase 1's status), which already show some routing unreliability at just 8 choices. Narrowing the field first is what makes the *existing* free-tier limitation survivable at 279 options instead of compounding it.
   - **Only the narrowed, selected few actually run** (real LLM calls, real cost). The rest stay exactly as the user wants: available, discoverable, zero cost, zero risk, until a future job's narrowing step surfaces them. This directly answers Phase 3.5's open item 7 ("279 agents... autonomously assignable by the AI Assistant per-project") — same underlying idea, now with an actual mechanism instead of a wish.
   - **Explicitly not required for this: agent-to-agent peer-to-peer communication.** That's a separate, harder concept (agents sharing learned knowledge or messaging each other directly, evaluated against `jcode`'s "Swarm" pattern and already deferred to Phase 6's peer-to-peer memory vision). Routing/selection only needs HQ deciding who to call — it doesn't need the called agents talking to each other.
   - **Not yet built** — this is the specified design to build against when this phase starts, not a completed item.
5. **`trigger.dev` as the real dispatch/background-job engine** (verified 2026-09-17 via GitHub API: 16.3k stars, MIT, TypeScript, "durable AI agents and workflows," Next.js-native, MCP support). This is the actual execution layer behind item 4's narrowed-down agent dispatch and behind long-running department jobs generally: durable background jobs, automatic retries, and scheduling, in the same TypeScript/Next.js stack GrowForge already runs — a genuine architectural fit, not an add-on. Candidate to sit alongside or eventually replace n8n for job execution (n8n stays relevant for external no-code workflow templates; trigger.dev is for GrowForge's own internal job orchestration). Not yet built — approved to proceed with when this phase starts.
6. **Structured "Voice DNA" + per-client "Audience Profile," upgrading the existing free-text `writingStyle` field** (specified 2026-09-18, after the user found Composio's "Claude Skills for Writing" writeup and asked what's worth taking). The article's real technique, verified by direct fetch rather than taken from its marketing framing: a **Voice DNA document** (explicit tone dimensions, sentence-structure preferences, a real banned/preferred vocabulary list, named "signature moves") plus a companion **Audience Profile** (reader role, knowledge level, reading context, the decision they're making) — used together instead of one vague style blob. Concrete fit for GrowForge: `userMemory.ts`'s `writingStyle` (currently a single free-text field, see `ProfileDashboard.tsx`'s "Writing Style & Tone" card) already covers half of "Voice DNA" — structuring it properly, and adding the missing "Audience Profile" half per client/project, would let department drafting (`runDepartments`/`runFinal` in `orchestrator.ts`) write for the actual client reading the plan instead of one generic GrowForge voice for every job. The article's "critique own draft against the voice spec, regenerate only the violating sections" loop is also a good refinement to the existing QA stage (`runQa` already reviews without rewriting — this would add a voice-compliance pass alongside the content-correctness one it already does). Not yet built — this is a real enhancement to an existing Phase 3 feature, not a new page.

**Exit gate:** At least one new capability (Meta Ads or BYO image-gen) proven live end-to-end, the same rigor as Phase 1's n8n proof — a real external action, independently verified, not just a 200 response.

## Phase 5 — AI Brain 3D Experience

**Goal:** The full holographic AI Brain vision — this is deliberately its own phase, not a UI tweak, because it's a real WebGL/3D build.

**Scope:**
1. **Warp transition** into User Profile — stars/light streaking past at extreme speed, settling into a holographic brain silhouette (zoomed out) that opens into a dark neuron-void of drifting light particles (zoomed in).
2. **Particle system** — agents/plugins/connectors as small particles, departments as slightly larger ones, soft pulsing glow traveling along connection lines (microscopic neuron-firing look). Departments positioned by function to a real brain-region metaphor (e.g. finance → the calculation region).
3. **Fully 3D and interactive** — slow constant self-rotation, click-and-drag 360° rotation, hover glow, click-to-inspect holographic overlays per particle (what it is, current activity, whether it needs an API key) that never interrupt the main view.
4. **Grows with real state** — adding tools/context visibly expands the brain; active items glow brighter than idle ones (backed by real status, not decorative).
5. **Vault Library as a 3D floating tree** — every agent/department browsable with its skills/tools/plugins/connect options, in the same visual language as the brain.
6. **Voice for the AI Assistant persona** (added 2026-09-17, per explicit product direction from the user). The product framing, confirmed with the user: the AI Assistant is the persona/face the user talks to; the AI Brain is that persona's brain (memory, departments, agents, tools); because the assistant is meant to eventually *become* the user's own second brain, giving it a voice is a real extension of the persona, not a bolt-on gimmick. Two candidate references were checked directly (GitHub API) at the user's request: `bigsk1/voice-chat-ai` (459 stars, Python, local/cloud speech-to-LLM-to-speech pipeline, supports Ollama) is a reasonable technical reference for the STT→LLM→TTS pipeline shape; `uezo/aiavatarkit` (672 stars, Python, VOICEVOX/VRChat/"waifu"-tagged) was evaluated and set aside — it's built for anime-style avatar companions, not a business-assistant voice, and would pull an unrelated visual-avatar rendering stack into scope. Neither is being adopted as a dependency; both are reference-only for when this item is actually built (likely Python-service-adjacent to the Next.js app, or a JS-native STT/TTS provider — not yet decided). Not yet built — sequenced here since it's part of the same persona experience as the Brain, not a separate phase.

**Exit gate:** The brain is real-time-data-driven (reflects actual connected tools/agent activity, not a static scene) and every interaction described above works, not just renders.

## Phase 6 — Self-Healing / Self-Learning Architecture

**Goal:** The system starts adapting itself based on real outcomes, not just executing a fixed pipeline.

**This is deliberately last of all.** A system that modifies its own prompts/logic based on outcomes needs the safety net Phase 0 built (the backtest harness) to be trustworthy *before* it's safe to build something that changes itself — otherwise a bad self-modification ships silently. This also covers the user's "agents teach themselves and remember everything, peer-to-peer" vision — a Notion-backed shared, role-scoped memory layer is the recommended foundation, built before any actual self-modification.

**Scope (intentionally not detailed yet — revisit and flesh out when this phase actually starts):**
- Start with logging/detecting failure patterns from real job history (read-only), before automating any change based on them.
- Shared, role-scoped agent memory (recommended: Notion API — structured/queryable, not a free-text document) before attempting agent-to-agent peer learning.
- Any self-modifying behavior needs a versioned rollback and a human-reviewed diff before it takes effect — no exceptions.
- **Reference architecture, verified 2026-09-17 against `1jehuang/jcode`** (an unrelated Rust terminal coding-agent harness, MIT, 19.8k stars — checked directly via the GitHub API, not taken on faith from a YouTube summary): its memory system embeds every agent turn as a vector, retrieves relevant past memories via cosine similarity (optionally double-checked by a small verifier side-agent before injection), and periodically consolidates/de-duplicates stale entries in the background. This is a solid concrete blueprint for the retrieval half of this phase's shared memory layer. It also directly diagnoses a real, already-present problem worth fixing as part of this phase: `growforge-ui/src/lib/userMemory.ts`'s `formatUserMemoryPrompt` (~line 315) currently injects *every* saved `brandRule`/`preference`/`learnedObservation`/`explicitRejection` into *every* pipeline stage's prompt, unranked and unbounded — exactly the failure mode embedding+retrieval is meant to prevent as the memory store grows. (jcode's "Swarm" — multi-agent same-repo file-conflict messaging — was also evaluated and does *not* apply here; GrowForge's departments run in parallel without shared-file contention, so that pattern isn't relevant scope for this phase.)

**Exit gate:** Not yet defined — define it when Phase 5 closes, informed by whatever's actually been learned by then.
